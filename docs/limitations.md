# 已知限制

按"会不会咬人"排序，不是按实现难度。

## 1. 虚拟桌面不是独立会话

这是本文最重要的一条。

| 你以为隔离了 | 实际情况 |
|---|---|
| 输入 | ❌ 同一输入队列。别的程序仍能往你的游戏里发键鼠事件；本插件自己不这么干，也不拦别人 |
| GPU / CPU / 内存 / 磁盘 | ❌ 完全共享。AI 桌面里跑 Android Studio，你游戏该掉帧还是掉帧 |
| 进程与权限 | ❌ 同一用户、同一 Session 1，权限完全相同 |
| 网络 / 注册表 / 文件系统 | ❌ 完全共享 |
| 窗口可见性 | ✅ **只有这一项**：AI 桌面上的窗口不会显示在你眼前 |

不要把本插件当沙箱。要真隔离得上 RDP 会话、Windows Sandbox 或虚拟机。

## 2. 启动瞬间一定会闪现

窗口创建的那一刻，它属于"当前显示的桌面"，然后才被移走。所以你会看到目标程序**闪一下**。

- 这是虚拟桌面的固有行为，没有绕过办法（除非程序支持完全无窗口启动）。
- `windowStyle:"minimized"` / `"hidden"` 能减轻，但**不保证**：部分程序（实测 Store 版记事本）忽略启动参数照样弹前台。
- 插件会如实返回 `foregroundStolen` 和 `windowStyleApplied`，不粉饰。

## 3. 截图抓不到的画面

`PrintWindow` + `PW_RENDERFULLCONTENT` 对大多数 Win32 / Electron / WPF 程序有效（实测 DSH 自己的 Chromium 窗口 2906×1550 抓得完整）。

抓不到或抓到空白的场景：

- DirectX / Vulkan 直出的游戏与 3D 视图
- DRM 受保护内容（播放器黑屏是故意的）
- 部分硬件覆盖层（overlay）渲染的窗口
- 全屏独占（exclusive fullscreen）程序

插件会用颜色采样检测"疑似空白"（`suspectedBlank` / `qualityVerdict:"blank_or_uncapturable"`），**不会**把空白当成功。但检测本身也可能漏：一个设计上真的纯色的界面会被误报。看到告警请自己判断。

WGC（Windows Graphics Capture）没有实现——它能抓到一些 PrintWindow 抓不到的东西，但需要额外处理 D3D11 设备和帧超时，属于后续工作。

## 3.5 UI Automation 读不到的东西

`vdm_uia_tree` / `vdm_uia_act` 依赖目标程序**自己实现** UI Automation provider。这不是插件能补的。

实测（Win11 25H2 / build 26200）：

| 目标 | 节点数 | 说明 |
|---|---|---|
| 文件资源管理器 | 95 | 完整，标题栏按钮标为可交互 |
| 记事本（Win11 版） | 7 | 只有外壳 + 标题栏；编辑区是独立渲染，UIA 里没有 Edit 控件 |
| 微信 / Steam | 1~4 | 自绘 UI，只暴露外壳 |
| DeepSeek Harness（Electron） | 12 | 只有标题栏按钮，**网页内容不暴露** |

因此：

- **Chromium / Electron 应用默认不向 UIA 暴露网页 DOM。** 程序自己带 `--force-renderer-accessibility` 之类的开关才可能拿到，这不是插件能强制的。
- **自绘界面（微信、游戏、多数国产客户端）整体不可见**，只能截图 + 人工确认。
- **窗口在别的虚拟桌面（cloaked）时内容可能退化**为只有外壳。`uia_tree` 的 `note` 会提示这一点，但退化本身无法避免。
- **`path` 是索引路径**（`0/2/1`），界面一变就指向别的控件。每次操作前重新跑 `uia_tree`，不要缓存、不要跨会话复用。
- **跨进程同步调用**：目标进程卡住时 UIA 调用也会跟着卡。插件先用 `IsHungAppWindow` 拒绝无响应窗口，但这只是第一道闸。
- **不支持的动作不会被"绕过"**：控件没有该 pattern 时返回 `succeeded:false` + `supportedPatterns`，插件**不会**退回坐标点击（那会打到用户前台）。真需要点某个位置，只能切到目标桌面并让用户授权。

## 4. 内部 COM 接口随时可能失效

`IVirtualDesktopManagerInternal` 是未公开接口，GUID 和 vtable 顺序靠社区逆向 + 社区标定。

- 只在 build ≥ 26100 放行，其他版本拒绝。
- Windows 大版本更新后可能整体失效，表现为 `desktopApiAvailable:false` 或 `interface_mismatch`。
- 失效不会把桌面搞乱：插件不做"猜一个方法试试"的事。

## 5. 应用商店版 / 转发壳程序

`C:\Windows\System32\notepad.exe` 这类转发壳，启动后立刻退出，真正 UI 在另一个进程。

插件的兜底策略：按进程名 + 启动时间（`>= launchedAt - 2s`）匹配窗口。

仍然可能出错的场景：

- 同名程序你本来就开着 → 启动时间过滤能挡住大部分，但快速连开多个同名实例时可能匹配错。
- 程序先起一个 splash 窗口再换主窗口 → 可能移走 splash 而不是主窗口。
- 一个程序多个顶层窗口 → 只移动评分最高的那个，剩下的留在原地。

返回值里 `windowMatchedByPid:false` 就是在告诉你"这个是猜的，动之前自己确认一遍"。

### 子窗口不能单独移动

`move_window` 对子窗口/控件（`GetAncestor(GA_ROOT) != hwnd`）直接拒绝，返回 `not_a_top_level_window`。
子窗口跟着父窗口走，单独移过去没有意义；而且拿到子窗口句柄通常意味着调用方抓错了 hwnd
（把按钮、编辑框当成了窗口）。拒绝比默默做一次无效操作好。

### 移动"就在用户眼前"的窗口会有警告

前台保护（`target_is_foreground`）挡的是"焦点正在这个窗口上"的情况。但用户可能焦点在别处、
眼前仍然摆着这个窗口（游戏被通知打断、切出去看了眼别的东西）。这类窗口被移走时，
返回里会带一条 warning：**这个窗口原本就在当前显示的桌面上，移走之后它会从用户眼前消失**，
并提示可以立刻移回。不下手阻止是因为有时确实需要移，但必须让调用方知道自己做了什么。

## 6. 关闭窗口可能卡住

`close_window` 只发 `WM_CLOSE`，行为等价于点窗口右上角的 ×。

- 程序弹"是否保存"对话框时，窗口不会消失，`stillOpen:true` 会告诉你。
- **不要反复发送 `WM_CLOSE`**，也不要强杀——可能丢数据。插件文案里就写着"交给用户处理"。
- 风险评级（`risk.level`）基于启发式：进程是否在文档/IDE 白名单、标题是否含 `*`/`•`/`[已修改]`、是否无响应、是否有模态弹窗。评级是**提示**，不是保证。
- 无窗口的程序（纯后台）没有 `WM_CLOSE` 可发，本插件不管它。

## 7. Game Mode 是策略约束，不是系统级封锁

Game Mode 拦的是**本插件自己**的工具调用。

- 它不会阻止别的插件、脚本或 AI 直接调 Win32 API。
- 它不改变系统输入状态、不挂钩子、不暂停前台程序。
- 用户手动删了 `state.json`，Game Mode 就没了（下次调用会按默认/保守状态重新开始）。

真正的保障是"AI 遵守约定 + 用户可随时关掉插件"。

## 8. 桌面枚举的边界

- 只能看到**当前用户、当前会话**的虚拟桌面。别的用户/别的会话的桌面看不到也管不了。
- 窗口列表以 `EnumWindows` 为基础，只含顶层窗口。子窗口、工具窗口默认不列（`includeHidden` 也救不了全部）。
- 刚创建、还没进 Shell 视图集合的窗口 `virtualDesktopId` 可能是 `null`，此时移动会失败——插件会重试一次，还不行就报错。
- `index` 只是当前排列顺序，用户增删桌面就变。**任何地方都不要持久化序号**，只认 GUID。

## 9. 多显示器与 DPI

- 虚拟桌面是"跨显示器"的概念，一个桌面可以横跨多个显示器；本插件不按显示器分组。
- 截图用的是窗口自身像素尺寸，混合 DPI 缩放下可能出现与你在屏幕上看到的物理尺寸不一致的情况。
- 插件自己声明了 PerMonitorV2，但**目标程序**如果是 DPI-unaware，PrintWindow 出来可能是缩放后的位图。

## 10. 不做的事

明确没实现，也不打算在 MVP 里实现：

- 全局鼠标键盘模拟（`SendInput`）——设计上就拒绝
- UIA 元素级自动化（`IUIAutomation`）——后续可加，现在只有窗口级操作
- 截整个桌面 / 指定显示器截图——故意不提供，避免截到你正在做的事
- 多用户 / RDP 会话管理
- 桌面壁纸、名称以外的桌面属性修改
- macOS / Linux 支持（虚拟桌面是 Windows 独占特性）

## 11. 性能与资源

- 每次工具调用都 spawn 一个新进程 `vdmhost.exe`（约 50KB，启动几十毫秒）。没有常驻进程，好处是崩了不拖累 DSH，代价是高频调用有开销。
- `list_windows` 默认上限 100 条（可到 500）。窗口特别多时（实测 130 个顶层窗口）会按上限截断并在文案里说明。
- 截图 PNG 存在 `~/.dsh/virtual-desktop-manager/captures/`，**不会自动清理**。长期用要自己删。
